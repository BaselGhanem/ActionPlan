# دار الدواء — خطة الأنشطة الطبية 2027

واجهة عربية متجاوبة بهوية دار الدواء، Firebase Authentication وFirestore مباشرة، وتعمل على Spark دون Cloud Functions أو خادم خارجي. الواجهة منشورة عبر GitHub Pages.

## التفعيل

افتح [صفحة التهيئة](https://baselghanem.github.io/ActionPlan/setup.html) واتبع خطوات نشر القواعد وإنشاء المسؤول الأول. لا يحتاج المستودع مفتاح خدمة أو كلمة مرور. لا تكفي إعدادات firebaseConfig وحدها لمنح صلاحيات الوصول.

1. فعّل Email/Password في Authentication وأضف baselghanem.github.io إلى Authorized domains.
2. انشر محتوى firestore.rules في Firestore > Rules.
3. أنشئ حساب Authentication بالبريد admin@users.dadactionplan.app وكلمة مرور تختارها.
4. أنشئ مستند setup/bootstrap في Firestore وفيه adminUid من نوع string بقيمة UID للحساب السابق.
5. ادخل باسم admin وكلمة مرورك. ينشئ النظام ملف المسؤول والتهيئة تلقائيا. أضف الفرق والميزانيات السنوية ثم القوائم والحسابات.

## العمليات

- جميع الفرق ترى العملاء والأنشطة ومبالغها؛ منشئ النشاط وAdmin وMarketing Manager يعدلون النشاط.
- Admin وحده ينشئ الحسابات ويرفع قوائم العملاء. المدير يدير الميزانيات والأنشطة وأنواعها والتقارير.
- قوالب Excel XLSX مستقلة لكل فريق: نزّل قالبا فارغا أو قائمة الفريق الحالية داخل القالب، ثم ارفع القالب الخاص بالفريق نفسه مع معاينة وتحقق من الأخطاء قبل الاستبدال. يقبل النظام 6 أعمدة ثابتة؛ الكود والاسم إلزاميان، والنوع والتخصص والمنطقة والتصنيف اختيارية. الكود نص للحفاظ على الأصفار الأولى، ولا يسمح بالرمز / أو بالأكواد المكررة؛ لا يقبل CSV أو اللصق الحر في شاشة الرفع.
- الكود يوحد العميل، آخر ملف يعتمد البيانات الأساسية، والتصنيف مستقل لكل فريق. الاستبدال يحفظ تاريخ الأنشطة ويمنع مشاركات جديدة للفرق المحذوفة من العميل. رفع غير مكتمل يوقف مشاركة الفريق مؤقتا؛ إعادة رفع قائمة كاملة تعيد تفعيله.
- النشاط الجديد يسجل الأطباء والعملاء كمشاركين فقط؛ توزع الميزانية المخططة والمصروف الفعلي مباشرة على الفرق المشاركة. لا تُطلب أي حصة مالية لكل طبيب، ويجب أن يطابق مجموع حصص الفرق إجمالي النشاط.
- المخطط يحجز ميزانية الفرق؛ والفعلي قابل للتسجيل والمتابعة مباشرة من تبويب «الفعلي والمتابعة» طوال 2027، ويحل فعلي كل فريق محل حصته المحجوزة عند تحويل النشاط إلى «منفذ». تمنع المعاملات الذرية تجاوز الميزانيات حتى مع الطلبات المتزامنة.
- إلغاء نشاط له فعلي للإدارة مع الاحتفاظ بالمصروف. حذف المخطط دون فعلي يعيد الحجز ويحتفظ بأثر التدقيق.
- التقارير تدعم الفرق والعملاء والشهر والنشاط والمنطقة والتخصص والتصنيف. الأنشطة المشتركة الجديدة لا تنسب حصصا مالية وهمية للطبيب؛ نشاط التخصصات المتعددة يظهر في مجموعة «متعدد التخصصات». تصدير Excel يفصل «التوزيع على الفرق» عن «المشاركون في الأنشطة».

## الحسابات

حساب واحد للفريق، باسم مستخدم وكلمة مرور. إنشاء الحساب من جلسة Firebase Auth ثانوية لا يخرج المسؤول. إعادة تعيين كلمة المرور تنشئ هوية Auth بديلة وتعطل ملف الهوية القديمة؛ يبقى accountId ثابتا لحفظ ملكية الأنشطة. لا تخزن كلمات المرور في Firestore. لإعادة تعيين كلمة مرور المسؤول نفسه استخدم Firebase Console. الهوية القديمة تبقى في Authentication ويمكن للمسؤول حذفها من Console، لكنها ممنوعة من بيانات التطبيق.

## التنفيذ والتحقق

```bash
npm ci
npm test
npm run test:firebase
npm run build
npm run test:sites
```

اختبارات Firebase تستخدم مشروعا محليا تجريبيا ومحاكيات Authentication وFirestore. لا تكتب على المشروع الحقيقي. نشر القواعد الحقيقي خطوة منفصلة من Console.

الأموال سنتات صحيحة. تعتمد القواعد وثائق تحقق غير قابلة للتعديل ثم معاملة واحدة للنشاط والميزانيات وسجل التدقيق. حتى 8 عملاء و8 فرق متأثرة لكل نشاط (بما فيها الفرق السابقة عند التعديل)، وهو حد معلن لتوافق حدود Firestore Security Rules. السنوات: 2027 حاليا.

Spark لها حصص مجانية محدودة للقراءة والكتابة والتخزين؛ التطبيق لا يفعل فوترة، وقد يتوقف عند استنفاد الحصة. التحقق متعدد الخطوات يزيد عدد العمليات لكل حفظ. يجلب التحميل الحالي قوائم السنة كاملة؛ الأحجام الكبيرة تحتاج ترقيم صفحات وتخطيطا لحصص الاستخدام. سجلات التدقيق والتحقق تحتفظ بتاريخها وتستهلك تخزينا. العرض التجريبي ?demo=1 يعمل في الذاكرة ولا يحفظ Firebase.

## Cascading Filters

- قوائم العملاء والتقارير متسلسلة ومتبادلة: خيارات كل فلتر تتغير حسب الفلاتر الأخرى، وتراعى نتائج البحث في دليل العملاء. التصنيف مرتبط بالفريق المختار، والتقارير تحتسب الأنشطة المشتركة على مستوى حصة الفريق دون تكرار.

## حذف العملاء للأدمن

- يمكن للأدمن حذف عميل واحد من دليل العملاء أو حذف جميع العملاء المطابقين للبحث والفلاتر؛ فلترة تخصص معين ثم الضغط على حذف النتائج تحذف ذلك التخصص ضمن الفلاتر المختارة. لا يمكن الحذف الجماعي دون اختيار فلتر أو بحث وتطلب كتابة كلمة «حذف».
- الحذف أرشفة من قوائم جميع الفرق النشطة، مع الاحتفاظ بمستند العميل وسجل الأنشطة السابقة والميزانيات؛ رفع قائمة جديدة تتضمن نفس الكود يعيد تفعيل العميل. لكل دفعة من عشرة عملاء معاملة وسجل تدقيق.
- يلزم نشر قواعد Firestore المحدثة يدويا؛ GitHub Pages ينشر الكود فقط.
- إصلاح favicon: الملف في public/favicon.ico والرابط يعتمد Vite BASE_URL ليعمل تحت /ActionPlan/.

- خيار «بدون تخصص» يظهر في فلتر التخصصات في دليل العملاء والتقارير للبيانات ذات التخصص الفارغ (بما في ذلك المسافات والقيم غير الموجودة)، ويعمل مع بقية الفلاتر المتسلسلة وحذف نتائج الفلاتر للأدمن.

## إصلاح موثوقية تحميل CSS

- بعد Vite build، يتم تضمين ملف CSS الناتج داخل `index.html` و`admin.html` بدلاً من طلب ملف CSS باسم hash مستقل من GitHub Pages. هذا يمنع ظهور خطأ 404 الخاص بملف CSS عند تحميل نسخة HTML بينما CDN لم يحدّث الملفات بصورة متزامنة.
- اختبار `npm run test:sites` يفحص وجود CSS المضمن بعد البناء. تأخر اتصالات Firestore Listen المؤقتة ليس دليلاً على خطأ الصلاحيات ما لم تظهر رسالة Firebase واضحة.

## تمييز الأطباء ذوي الأنشطة
- يحدد النظام وجود Activity اعتمادا على كود العميل عبر جميع الفرق، وليس الاسم أو الفريق. يعتبر النشاط المخطط والمنفذ والملغي نشاطا مسجلا؛ ولا تدخل الأنشطة المحذوفة في الحساب.
- يستخدم مؤشر تقويم بجانب أسماء الأطباء (ليس الصيدليات أو المستشفيات) في دليل العملاء، اختيار العملاء، توزيع النشاط، سجل الأنشطة، تقارير العملاء ومعاينة رفع العملاء. يحمل المؤشر عددا موضحا عند المرور عليه.
- يضاف فلتر Activity في صفحة دليل العملاء بقيم «جميع العملاء» و«لديهم Activity» و«بدون Activity»، مرتبطا بالـ Cascading الحالي. الفلتر يشمل جميع فئات العملاء، وليس الأطباء فقط، وتستمد نتيجته من الأنشطة المخزنة في السنة المعروضة 2027. لا حاجة إلى تغيير Firebase Rules.

## تقرير حسب التخصص
- أضيف تبويب «حسب التخصص» إلى التقارير، بنفس أعمدة «حسب الفرق»: التخصص، عدد الأنشطة الفريدة، المبالغ المخططة غير الملغاة، والفعلي. يعمل مع جميع الفلاتر الحالية بما فيها «بدون تخصص».
- تنسب المبالغ حسب حصص العملاء والفرق **المحفوظة حاليا** من دون افتراض توزيع جديد؛ النشاط متعدد الفرق داخل التخصص الواحد يحتسب مرة في عدد الأنشطة، بينما المبالغ تجمع مرة لكل حصة مالية.
- تم اعتماد نموذج الأنشطة الجديد schema 3 للميزانيات على مستوى الفرق وحدها. يحتفظ النظام بقدرة قراءة الأنشطة القديمة schema 2؛ وعند تعديلها يستخدم نموذج الفرق الجديد. اختُبر إنشاء وتعديل واحتساب الميزانيات في المحاكي، لكن تحويل نشاط قديم بعد إعادة تعيين هوية منشئه لم يثبت نجاحه في اختبار التكامل ويحتاج فحصا منفصلا.

## واجهة تحرير النشاط والتشغيل السنوي

- نموذج النشاط نافذة Popup مركزية بعرض كبير على سطح المكتب وشاشة كاملة قابلة للتمرير على الهاتف، بدلا من لوحة جانبية.
- تبويب مستقل «الفعلي والمتابعة» يعرض الأنشطة المخططة والمنفذة مع البحث، وحفظ مصروف فعلي مبدئي لكل فريق أو اعتماد النشاط كمنفذ. لا يتطلب توزيع المصروف لكل طبيب.
- يلزم إعادة نشر firestore.rules المعدلة من خلال Firebase Console بعد نشر واجهة GitHub Pages، لأن النموذج الجديد schema 3 لن يحفظ مع قواعد schema 2 القديمة.

## ميزانية لوحة التحكم وتفاصيل التكلفة
- في لوحة التحكم فقط، العمود الذي كان عنوانه «المتاح USD» أصبح بعنوان أوضح «المتبقي من الميزانية USD»، وقيمته هي الميزانية السنوية للفريق ناقص المحجوز والمصروف. لا تغيير في جدول الفرق الموجود بالتقارير.
- يمكن من نافذة النشاط الكبيرة إضافة حتى 8 بنود تفصيلية اختيارية للميزانية: تكلفة مرتبطة بالعميل، غداء/ضيافة، مكان، تجهيزات، وأخرى، مع تعديل الوصف والقيمة. عند إضافة أي بنود، يجب أن يساوي مجموع قيمها إجمالي النشاط عند الحفظ.
- مثال: نشاط 1,500 USD = تكلفة مرتبطة بالعميل 1,000 USD + غداء 500 USD. تفاصيل البنود لا تنشئ حصصا مالية للأطباء، ولا تضاعف الحجز على فرق العمل؛ توزيع المبالغ والفعلي يظل حسب الفرق فقط.
- عند تعديل نشاط سابق بلا بنود لا تظهر تفاصيل افتراضية؛ يمكن إضافتها عند الحاجة. يضاف تصدير تفاصيل البنود في ورقة Excel مستقلة. يلزم نشر Firestore Rules المحدثة يدويا لتفعيل حفظ هذه التفاصيل في Firebase.

## Cost-first budgeting workflow
- نشاط جديد يبدأ ببندي Honorarium / أتعاب الأطباء وغداء / ضيافة بقيم فارغة. يُحسب إجمالي النشاط من بنود التكلفة تلقائياً، ويوزع بالتساوي افتراضيا على الفرق المحددة؛ يظل تعديل حصص الفرق يدوياً متاحاً.
- عند تغيير الإجمالي بسبب تعديل أي بند تكلفة، يعاد التوزيع بالتساوي، وعند ثبات الإجمالي تُحفظ تعديلات حصص الفرق اليدوية. الصفوف الفارغة (صفر) لا تحفظ.
- الأنشطة القديمة التي لا تحتوي تفاصيل تكلفة تستمر بتعديل إجمالي النشاط يدوياً كما كانت.

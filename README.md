# دار الدواء — خطة الأنشطة الطبية 2027

واجهة عربية RTL بهوية Dar Al Dawa، مبنية بـ React + Vite وتنتج HTML/CSS/JS ثابتة، مع Firebase Authentication وFirestore وCloud Functions.

## ما تم تنفيذه

- شاشة العملاء بفلاتر الفريق والتخصص والمنطقة والتصنيف ونوع العميل والاسم/الكود.
- نموذج توزيع جانبي على اللابتوب، وشاشة كاملة مع اختيار عدة عملاء على الموبايل.
- النشاط يسجل مرة واحدة. إجمالي حصص العملاء يطابق الإجمالي، وحصص الفرق تطابق حصة كل عميل.
- الاختيار الافتراضي لفريق المستخدم إذا كان يزور العميل، مع إمكانية إلغائه.
- توزيع متساو بالسنتات دون فروق تقريب، وتعديل يدوي لكل حصة.
- جميع الفرق ترى العملاء والأنشطة والمبالغ؛ التعديل لمنشئ النشاط والإدارة.
- المخطط يحجز الميزانية عند الحفظ. الفعلي يسجل أثناء التنفيذ، ويحل محل المخطط عند إغلاق النشاط.
- يمنع تجاوز ميزانية أي فريق، حتى عند تعديل نشاط قائم أو تسجيل الفعلي. تعديل الميزانية لا يسمح بالنزول دون المستخدم.
- إلغاء نشاط له فعلي للإدارة فقط مع إبقاء الفعلي محسوبا. حذف النشاط المخطط دون فعلي يعيد الحجز ويبقي أثر التدقيق.
- Admin: رفع العملاء واستبدال قائمة الفريق، الحسابات، الميزانيات، أنواع الأنشطة، وسجل آخر 100 تغيير.
- Marketing Manager: جميع العمليات عدا إدارة المستخدمين ورفع/إدارة قوائم العملاء.
- رفع XLSX وCSV ولصق جدول، معاينة وربط أعمدة، وكشف أكواد مكررة وحقول ناقصة قبل الرفع.
- نفس كود العميل عبر الفرق، والتصنيف لكل فريق. بيانات العميل الأساسية تعتمد آخر رفع.
- حذف العميل من قائمة الفريق يمنع مشاركته الجديدة فقط، ويحفظ علاقاته داخل الأنشطة السابقة.
- تقارير حسب الفرق والعملاء والشهر ونوع النشاط، مع فلاتر المنطقة والتخصص والتصنيف والحالة.
- تصدير Excel شامل بخمس أوراق منسقة: الفرق، العملاء، ارتباطات الفرق، الأنشطة، والتوزيعات.

## الحالة الفعلية

الواجهة وأكواد الخلفية مجهزة. لا يكفي firebaseConfig لنشر وظائف الخادم أو منح الحساب الأول صلاحية Admin. لا توجد مفاتيح خدمة أو كلمات مرور داخل المستودع. يجب إتمام التهيئة التالية في مشروع dadactionplan قبل إدخال بيانات حقيقية.

## تشغيل محلي

```bash
npm ci
npm run dev -- --host 0.0.0.0 --port 4173
```

`?demo=1` يفتح بيانات توضيحية منفصلة في الذاكرة فقط. لا يكتب إلى Firebase، وتختفي تعديلاته عند إعادة التحميل.

## نشر الواجهة

GitHub Actions في `.github/workflows/pages.yml` يبني الواجهة تلقائيا من main وينشر `dist/client` إلى GitHub Pages. قد يحتاج أول نشر اختيار GitHub Actions كمصدر Pages في Settings > Pages. ينشأ `admin.html` من نفس التطبيق ويبدأ على قسم الإدارة بعد تسجيل الدخول. حساب الفريق لا يحصل على صلاحيات الإدارة من تغيير عنوان الصفحة.

## تفعيل Firebase — مرة واحدة

1. في Firebase Authentication فعل Email/Password، وأضف `baselghanem.github.io` إلى Authorized domains.
2. أنشئ Firestore في Native mode إذا لم يكن جاهزا.
3. نشر Cloud Functions يتطلب مشروع Blaze، وحساب Google لديه صلاحية نشر الوظائف والقواعد. لا تفعّل الفوترة تلقائيا دون قرار مالك المشروع.
4. من نسخة المستودع على جهازك، سجل الدخول وانشر:

```bash
npm install -g firebase-tools
firebase login
npm --prefix functions install
firebase deploy --only functions,firestore --project dadactionplan
```

5. أنشئ حساب Admin الأول في Firebase Authentication من Add user، بالبريد الداخلي `admin@users.dadactionplan.app` وكلمة مرور تختارها بنفسك. هذه العناوين تقنية لتشغيل تسجيل الدخول باسم مستخدم ولا تستقبل البريد.
6. انسخ UID للحساب. في Firestore أنشئ collection باسم `users`، وdocument ID يساوي UID، بالحقول التالية:

| الحقل | النوع | القيمة |
|---|---|---|
| username | string | admin |
| name | string | مسؤول النظام |
| role | string | admin |
| active | boolean | true |
| teamId | null | null |

7. ادخل باسم `admin` وكلمة المرور التي أنشأتها، ثم أضف الفرق والميزانيات، أنواع الأنشطة، ارفع القوائم، وأنشئ حسابا لكل فريق وحساب Marketing Manager.

بديل اختياري لكتابة profile يدويا: `scripts/bootstrap-admin.mjs` من بيئة لديها Google Application Default Credentials، مع توفر firebase-admin. السكربت يربط حساب Authentication موجودا ولا يطلب كلمة مرور.

## ملف العملاء

الصف الأول عناوين. الأعمدة: كود العميل، اسم العميل، نوع العميل، التخصص، المنطقة، التصنيف. الكود والاسم إلزاميان؛ القيم الأخرى اختيارية. يدعم ربط أسماء أعمدة مختلفة. احفظ الكود كنص للحفاظ على الأصفار الأولى. لا يسمح بالرمز `/` داخل الكود. حد الدفعة 200 سجل ويرفع الملف على دفعات، ثم يستبدل مؤشر قائمة الفريق بعد نجاح الرفع.

## النموذج المالي

جميع القيم مخزنة كسنتات صحيحة. سجل ميزانية الفريق يحتوي budget وused. حفظ/تعديل/حذف النشاط وتعديل used يحدث في Firestore transaction واحدة، لذلك تعاد محاولة العمليات المتزامنة ويمنع تجاوز الرصيد من واجهتين متزامنتين. قرارات الصلاحية تتم على الخادم. القراءة والكتابة المباشرة لبيانات الأعمال مغلقة بالقواعد.

الفعلي الظاهر في لوحة التحكم للمتابعة قد يتداخل مع المخطط المحجوز لنفس النشاط؛ لا يجمع المؤشران باعتبارهما تكلفة واحدة. تقرير التصنيف يستخدم تصنيف القائمة الحالية، بينما الاسم/المنطقة/التخصص في الأنشطة تحفظ عند حفظ النشاط. آخر 100 تغيير متاحة للعرض؛ السجلات الأقدم لا تحذف من قاعدة البيانات.


اختبارات توزيع السنتات، مطابقة حصص العملاء والفرق، الفعلي، الإلغاء، وصحة التاريخ. تم اختبار تدفق الواجهة في المتصفح ببيانات المعاينة. اختبارات نشر Firebase الحقيقي والمستخدمين والمعاملات المتزامنة الفعلية تحتاج تفعيل المشروع أولا، ولم يتم الادعاء بتشغيلها قبل النشر.

التحميل الحالي يجلب جميع العملاء والأنشطة النشطة للسنة في طلب واحد. مناسب للانطلاق؛ القوائم الضخمة جدا تحتاج pagination من الخادم ونسخة تصدير بالخادم قبل التوسع. النشاط الواحد يدعم حتى 100 عميل.
